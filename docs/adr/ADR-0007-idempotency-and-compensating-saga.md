# ADR-0007 — Idempotency و Saga جبرانی در تحویل

- **وضعیت:** پذیرفته‌شده
- **متنازع:** دو سیستم مالی مستقل (درگاه و تامین‌کننده) در یک تراکنش واحد جا نمی‌شوند.

## سناریوهای شکست و پاسخ طراحی

| سناریو | ریسک | کنترل در کد |
|---|---|---|
| کاربر دو بار روی «پرداخت» می‌زند | دو سفارش / دو خرید | `runOnce({ key, fingerprint })` — کلید یکسان + بدنه متفاوت → `IdempotencyConflictError` |
| Callback درگاه دو بار می‌رسد | دو بار شارژ کیف پول | همان `runOnce` + `txId` پایدار در دفتر |
| دو درخواست هم‌زمان | خرید دوباره از تامین‌کننده | `IdempotencyInFlightError` (پاسخ 409 به درخواست دوم) |
| پرداخت موفق، تامین‌کننده خطا می‌دهد | پول گرفته، کالا تحویل نشده | ریفاند خودکار به کیف پول + اطلاع کاربر + تیکت ادمین |
| خطای شبکه/Timeout در خرید | وضعیت واقعی نامعلوم است | **ریفاند نمی‌دهیم**؛ `retry_scheduled` + DLQ با دلیل `transport_error` |
| تامین‌کننده `delivered` می‌گوید ولی لایسنس خالی است | کاربر بدون کالا | DLQ با `delivered_without_accounts` + تیکت؛ بدون ریفاند کور |
| تامین‌کننده می‌گوید `failed` ولی `refunded=false` | اعتبار USD ما سوخته | ریفاند به کاربر + DLQ `supplier_did_not_refund` جهت پیگیری دستی |

## تصمیم

کلید Idempotency ارسالی به تامین‌کننده = شناسه داخلی سفارش (پایدار، حداکثر ۶۴ کاراکتر، هرگز تصادفی). تلاش مجدد باید **همان** کلید را بفرستد. ترتیب اجباری: برداشت از کیف پول ← خرید تامین‌کننده ← مهروموم لایسنس ← اطلاع.

## پیامد

- جدول `idempotency_keys` با `UNIQUE(key)` و `fingerprint` لازم است.
- هر رکورد DLQ باید قابل Replay دستی باشد؛ Replay با همان کلید خرید دوم نمی‌سازد.
